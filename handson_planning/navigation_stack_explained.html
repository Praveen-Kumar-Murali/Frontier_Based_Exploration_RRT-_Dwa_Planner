📊 Log-Odds Accumulation — How Confidence Builds

Each cell stores one float. It goes up when hit, down when a free ray passes through. Think of it as a vote counter:

Start — no evidence
0.00 → UNKNOWN (grey in RViz)
After 1 LiDAR hit (+0.85)
0.85 → still unknown
After 2 hits (0.85 × 2)
1.70 → still unknown
After 3 hits (0.85 × 3 = 2.55) — threshold = 2.0 ✅
2.55 → WALL (black = 100)
After 3 free rays (−0.20 × 3 = −0.60) — threshold = −0.5 ✅
−0.60 → FREE (white = 0)
# The actual code in to_ros_array()
out[self.grid >  2.0] = 100  # wall (3+ hits)
out[self.grid < -0.5] = 0    # free (3+ free rays)
# everything else = -1 (unknown/grey)

🔒 Sticky Walls — Preventing False Erasure

A confirmed wall cell (log-odds > 2.0) is protected from free-ray erasure:

for c, r in cells[1:-1]:      # intermediate cells
        if self.grid[r, c] < 2.0:  # sticky wall check
        update_cell(c, r, l_free)
⚠️
Why needed? Sensor noise, simulator artifacts, or glass surfaces can cause a beam to "pass through" a thin wall. Without sticky walls, that single ghost free-ray would erase a confirmed wall, creating a fake gap the robot tries to drive through.
🔑
The trade-off: Once a cell is locked as a wall, it can never be corrected. We accept this because false-positive walls are safer than false-negative gaps.

📐 Bresenham Ray Casting — Finding All Cells a Beam Crosses

When a laser beam travels from sensor to wall, it crosses many grid cells. We need to mark all intermediate cells as FREE and only the endpoint as WALL. Bresenham's algorithm finds every cell the line touches using only integer arithmetic — no floating point, no gaps, no duplicates.

The algorithm tracks an err term. When the error crosses a threshold, it steps in the row direction; otherwise it steps in the column direction. This traces the nearest-pixel approximation of a straight line.

# Pseudocode of what Bresenham gives us:
sensor at (col=2, row=2), hit at (col=8, row=5)

Cells traced:
(2,2) → FREE  ← sensor cell
(3,2) → FREE
(4,3) → FREE
(5,3) → FREE
(6,4) → FREE
(7,4) → FREE
(8,5) → WALL  ← endpoint: +0.85

🟠 global_planner.py — RRT* Path Planning

RRT* Algorithm Flowchart

🏗 C-Space Inflation — The Key Concept

Before RRT* runs, every wall cell is expanded outward by the robot's radius (0.16m). This converts the planning problem from "robot with a body" to "point robot" — much simpler to solve.

Unknown cells (−1) are not inflated — this lets RRT* plan through unexplored space during live mapping.

🔁 Online Replanning — Keeping the Path Safe

🔵 dwa_planner.py — Dynamic Window Approach

Three-Phase State Machine — Every 100ms

🎯 Trajectory Scoring — The Math

Every one of the 168 trajectories gets a single score. The highest-scoring non-blocked trajectory wins:

# 1. Heading — does endpoint face waypoint?
head_err = angle_between(endpoint_dir, waypoint_dir)
h_sc = 1.0 - head_err / math.pi   # 1.0=perfect

# 2. Clearance — distance to nearest wall
c_sc = min(min_wall_dist / 0.6, 1.0)  # 1.0=far

# 3. Velocity — forward progress
v_sc = min(distance_travelled / max_dist, 1.0)

# Final weighted score
score = 3.0*h_sc + 0.5*c_sc + 0.3*v_sc
📊
Heading dominates (weight 3.0). The robot goes the right direction first, avoids walls second (0.5), and prefers speed third (0.3). Near a wall on one side, clearance score biases the green arc away from it.

🛡 The Step-0 Skip — Why It Matters

During trajectory simulation, the first step is skipped for collision checking:

for step in range(sim_steps):
    px += v * cos(pth) * dt
    py += v * sin(pth) * dt
    pth = atan2(sin(pth+w*dt), cos(pth+w*dt))
        if step == 0: continue  # skip step 0!
    if map_inf[row, col] == 100:
        return None  # collision
⚠️
After C-space inflation, cells adjacent to the robot may be marked occupied (because the robot is next to a wall). Checking step 0 would mark every trajectory as blocked — the robot would freeze permanently. Skipping step 0 acknowledges that the robot's current position is valid.

🐛 The Three Most Critical Bugs Fixed

🔴 Infinite Replan Loop
Cause: path_index never advanced → replanner kept checking already-traversed segments (now blocked by freshly-mapped walls) → triggered new plan → same loop forever.
Fix: Advance path_index in _odom_cb as robot passes each waypoint. Check only the next 2 waypoints ahead.
🔴 Robot Freezes Every 2s
Cause: _stop() was called before the new plan was ready → DWA received an empty path → stopped moving → stood still for up to 2 seconds every replan cycle.
Fix: Never call _stop() when replanning. DWA keeps the old plan until the new plan arrives.
🔴 DWA Never Moved Forward
Cause: Dynamic window v_hi = vx + a_v×dt ≈ 0.04 m/s from rest. At that speed, heading score was low and all trajectories scored near 0.
Fix: Always sample full range linspace(0, v_max). Ignore acceleration limit for velocity window.

🎓 Questions to Ask the Professor

Grouped by topic, ordered from concept → implementation → next phase. Each question shows depth of understanding, not just "it works."

On Mapping

Q1: Our sticky-walls rule makes confirmed wall cells permanent — a false positive can never be corrected. What would be a better approach, and what real-time trade-offs does it introduce?
Shows you know the correctability trade-off. Expected direction: bounded log-odds decay (e.g. multiply by 0.99 per timestep), or a dual-threshold with "strong wall" vs "soft wall" states. Trade-off: computational cost vs. ability to correct mapping errors from glass, mirrors, or moving objects.
Q2: We use Bresenham for ray casting — it's a nearest-pixel approximation. What accuracy do we lose compared to a probabilistic beam model, and in what real-world scenario would the difference matter most?
Bresenham gives binary free/occupied; a Gaussian range model accounts for sensor noise distribution. Matters most in narrow doorways (1–2 cells wide) where beam model would show graded probability vs. Bresenham's hard boundary.

On RRT*

Q3: RRT* is asymptotically optimal — path cost converges to the global optimum as iterations → infinity. We stop at 5000. How would you detect convergence early to stop wasting computation?
Track the path cost delta between the last N goal-connecting events. If the cost improvement falls below a threshold (e.g. <1cm), declare convergence. Or use Informed RRT* — once a path is found, only sample within the ellipse defined by the current path length.
Q4: We inflate the map before planning but do not inflate unknown cells. The robot can plan through unexplored space. In what scenario is this assumption dangerous, and how would you handle it conservatively?
Dangerous when unknown space is actually a narrow passage or dead-end. Conservative fix: treat unknown cells as occupied during planning (pessimistic map). More balanced: use a risk-weighted cost function that penalises paths through unknown cells but doesn't block them entirely.

On DWA

Q5: DWA simulates trajectories using a kinematic unicycle model. The real robot has motor inertia, wheel slip, and control latency. How does this model-reality gap affect safety guarantees?
The actual robot may deviate from the simulated trajectory — especially at high angular velocities. The robot could end up closer to a wall than DWA predicted. Fix: add a safety margin to collision checks (check at robot_radius + δ), or use a full dynamic model with motor transfer functions.
Q6: Our scoring weights (3.0, 0.5, 0.3) were tuned manually. Is there a principled learning approach? What data would you need?
Inverse Optimal Control (IOC) / Inverse Reinforcement Learning. Data needed: demonstrations of an expert driver navigating through the same environment. The algorithm infers the weight vector that best explains the expert's trajectory choices. The challenge is defining the feature space to match the three criteria.

On Phase 2 — Dubins Paths

Q7: Dubins paths assume constant speed and a minimum turning radius — car-like motion. Our robot is differential drive and can turn in place. When does using Dubins paths still make sense on a diff-drive robot?
Dubins is useful when the robot needs to arrive at a goal with a specific heading (e.g. docking, parking). At cruising speed, the minimum turning radius constraint is real even for diff-drive (wheel slip, stability). Breaks down in tight spaces where in-place rotation is the only option. Solution: use Reeds-Shepp curves which allow reverse motion and zero-radius turns.

On Phase 3 — Frontier Exploration

Q8: Frontier exploration — "nearest frontier" is the simplest strategy. What is the information-theoretic argument for choosing frontiers by expected map entropy reduction instead?
Shannon entropy of the occupancy grid = Σ −p log p over all cells. Nearest frontier is greedy and may lead to a dead-end that only opens a small new area. An entropy-maximising frontier opens the most new information per unit travel distance. In practice, cost-utility functions like I(F) = info_gain(F) / travel_cost(F) are used — similar to mutual information in active SLAM.
Q9: In the two-level hierarchy (RRT* global + DWA local), what are the fundamental limitations compared to a unified trajectory optimiser like TEB (Timed Elastic Band)?
Key limitation: the global plan is computed on a static map snapshot and passed down as fixed waypoints. DWA must correct this locally but can't change the global topology. TEB optimises the entire trajectory simultaneously — it can deform the path globally if a new obstacle appears mid-route. Trade-off: TEB is much more computationally expensive and harder to tune. RRT*+DWA is simpler, more predictable, and faster to debug.
